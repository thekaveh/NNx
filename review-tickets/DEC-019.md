## Summary

DEC-019: Run-bundle JSON files are bounded at 64 nesting levels, on the premise that this is "deeper than any NNx state". It is not: a model spec config may nest 256 levels, and every encoded mapping or tuple takes two JSON levels, so a config nested more than 28 levels already cannot be bundled. Today `export_bundle` stages the files, fails the read-back with a message that does not name the bound, and removes them. The owner must decide: refuse up front with a clear message (A), raise the bound (B), or keep it and document it (C).

## Context

**What happens today.** The bound and its premise (`src/nnx/bundles.py` L112):

```python
_MAX_DEPTH = 64  # nesting deeper than any NNx state: refused before a recursive walk
```

A spec config is frozen under the library-wide bound (`src/nnx/_config.py` `_freeze_config`, L62–L63):

```python
    if too_deep(value, MAX_JSON_DEPTH):
        raise ValueError(f"{owner} config{path} nests more than {MAX_JSON_DEPTH} levels")
```

with `MAX_JSON_DEPTH = 256` (`src/nnx/_json_depth.py` L24). `_encode` (`bundles.py` L282–L330) writes a string-keyed mapping as `{"$dict": {...}}` and a tuple as `{"$tuple": [...]}`, two JSON levels each. In `state.json`, a `ModelSpec` config sits under `checkpoint` → `model_params` → `net` → `config`, so a config whose deepest mapping is level *d* nests 7 + 2*d* JSON levels: 64 is passed at *d* = 29. `export_bundle` writes the generation directory, then reads it back (`_read_generation(..., full=True)`, L1322) and only there refuses it. After FIX-122 the error is `BundleIntegrityError("the state.json file nests more than 64 levels")`; the staged directory is removed and the previous bundle stays published (`tests/test_bundle_validation.py` `test_a_staged_generation_readers_would_reject_is_never_published`, L604–L628, pins this with 40 nested tuples in a callback's state).

**Why it matters.** A run that trains and checkpoints fine cannot be exported, and the message does not say that a bundle has its own, lower bound or what to do.

**History.**
- #551 (FIX-083) bounded JSON depth library-wide and kept the bundle bound on purpose. Its Scope Out: "The bundle limit of 64." So the bound is a recorded decision; this ticket only revisits it because its premise is false.
- FIX-122 (BUG-22 part 2) makes `bundles._parse_json` a wrapper over the shared `_artifacts.parse_json` with `max_depth=_MAX_DEPTH`, keeps `_MAX_DEPTH = 64`, deletes `bundles.py`'s `from ._json_depth import too_deep` import and re-matches the depth tests to `the state.json file nests more than 64 levels`. This ticket is written against the code as FIX-122 leaves it.
- #218 made the artifact loaders strict JSON.

**Background for the worker.**
- Run bundle: the data-only export of a run (`export_bundle`): `bundle.json` plus a `g-<generation>/` directory with `state.json`, safetensors payloads and `calibrator-<n>.json` records. Readers (`validate_bundle`, `inspect_bundle`, `reconstruct_bundle`) refuse a JSON payload nested past `_MAX_DEPTH`.
- `too_deep(value, limit)` (`_json_depth.py` L29–L41): whether a value nests more than `limit` levels of mappings and lists (`{}` and `[]` count one; scalars none), without recursion.
- `BundleError` (`bundles.py` L121): a bundle that cannot be made or used; `BundleIntegrityError` (L125) subclasses it for a malformed or tampered bundle.
- `ModelSpec(id, version, config)`: a registered model factory's spec; `register_model_factory(id, version, factory)` registers the callable that builds the net from `config`.
- PyYAML writes `run.yaml` recursively, so a test config of 100 levels is safe where 256 is close to the default recursion limit.

## Options

| Option | What changes | Trade-off |
|---|---|---|
| A (recommended) | `export_bundle` checks each JSON payload against `_MAX_DEPTH` before anything is written and raises `BundleError` naming the bound and the two-levels-per-mapping rule. The bound stays 64 (#551). | A clear, early refusal with no staged files; no format or reader change. A config nested 29–256 levels still cannot be bundled. |
| B | Raise `_MAX_DEPTH` to `2 * MAX_JSON_DEPTH + 8` (520), enough for a 256-level config in `state.json`; keep the safetensors rank check at 64 with a new `_MAX_RANK`. | Every config NNx accepts can be bundled. Readers accept 8× deeper files, and the recursive encode/decode walks run about 520 frames deep on Python 3.11, half the default recursion limit. Reverses #551's recorded bound. |
| C | Keep everything; document the bound and the 28-level consequence in the `export_bundle` docstring and fix the `_MAX_DEPTH` comment. | No code change; the refusal stays late (after staging) and its message stays generic. |

A is recommended because it keeps #551's bound and the readers unchanged, and turns a late, unexplained refusal into an early one that says what the limit is.

**If option A, the worker does:**

3. In `export_bundle`, directly before `json_payloads = {_STATE: _dumps(state)}` (L1286), insert:

   ```python
       # Readers refuse a JSON payload nested past _MAX_DEPTH, and an encoded mapping or tuple takes two
       # levels ({"$dict": {...}}): refused here, before anything is written, with the bound named.
       payloads = {_STATE: state, **{f"calibrator-{i}.json": c.state() for i, c in enumerate(calibrators)}}
       deep = [name for name, value in payloads.items() if too_deep(value, _MAX_DEPTH)]
       if deep:
           raise BundleError(
               f"run {run_id!r} cannot be bundled: {', '.join(deep)} would nest more than {_MAX_DEPTH} JSON levels, "
               "the run-bundle bound (each mapping or tuple in a config or training state takes two); keep this "
               "run in its pickle checkpoints"
           )
   ```
