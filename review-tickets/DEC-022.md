## Summary

DEC-022: `.maintenance/` holds two run logs of past automated maintenance passes (2026-07-01 and 2026-07-22). Nothing references them, they are not shipped, and their content is stale. The owner must decide whether they are removed (A), archived in a closed issue and removed (B), or kept with a "historical record" header (C).

## Context

**What happens today.** The two files open with their own status lines (`.maintenance/overnight-2026-07-01.md` L1–L5):

```markdown
# 1. Overnight Maintenance Ledger: 2026-07-01

**Status:** Superseded and incomplete. The run stopped after pass 4 of 75
without reaching its required 25 consecutive zero-issue passes. Its findings
remain historical evidence, not a completed maintenance certification.
```

and (`.maintenance/overnight-2026-07-22.md` L1–L5):

```markdown
# 1. Overnight Maintenance Ledger: 2026-07-22

**Status:** Capped without convergence. All findings discovered through Pass 50
were repaired and final automated verification passed, but the run did not
reach 10 consecutive global zero-finding passes before `--max-passes 50`.
```

Their content no longer matches the repository: the 2026-07-01 ledger names a working branch that no longer exists (L9–L10), cites `mkdocs.yml` as a tracked file (L36; it is now generated and git-ignored), says Dependabot covers "pip" (L37; it covers `uv`) and calls pyright "advisory" (L38; `ci.yml` L82 gates on it).

**Why it matters.** Stale operational notes at the repository root read as current guidance to a contributor, and they describe tooling that has changed.

**History.** No board issue covers these files. `grep -rn "\.maintenance" --exclude-dir=.git .` finds no reference anywhere; `MANIFEST.in` does not ship them. The CHANGELOG mentions "overnight-maintenance passes" in released sections (for example 0.2.0, L652–L656); those entries are history and stay. DOC-23 (FIX-140) fixes the stale `mkdocs.yml` comment in `.gitignore` and leaves the ledger to this ticket.

**Background for the worker.**
- The GitHub wiki is generated: `scripts/docs/push_wiki.py` "Replace[s] the GitHub wiki master branch with generated pages" built from `docs/manifest.yaml` on each publish, so a page added by hand to the wiki is deleted on the next publish. That is why no option moves the ledgers to the wiki (the review suggested it); option B archives them in an issue instead.
- `docs/manifest.yaml` lists the published pages; the ledgers are not in it, so neither the site nor the wiki shows them.

## Options

| Option | What changes | Trade-off |
|---|---|---|
| A (recommended) | `git rm -r .maintenance`. | The root holds only maintained files. The text stays in git history (`git log -- .maintenance`). |
| B | Copy both ledgers into one closed issue, then `git rm -r .maintenance`. | Searchable on the board as well as in git history. One more closed issue that nobody maintains. |
| C | Keep both files and add a "historical record" note under each title. | Nothing is lost from the working tree. The stale lines stay at the root, labelled. |

A is recommended because the files are unreferenced, unshipped and stale, and git history already keeps them.

**If option A, the worker does:**

1. `git rm -r .maintenance`.
2. No CHANGELOG entry: nothing user-facing changes.

**If option B, the worker does:**

1. Create the archive issue (needs `gh` with repository write access; if the worker has none, the owner runs this command):

   ```bash
   {
     echo "Archived from \`.maintenance/\` at 9ad461e (DEC-022). Historical record only: the branches, files, tools and CI settings these ledgers name may have changed since."
     for f in .maintenance/overnight-2026-07-01.md .maintenance/overnight-2026-07-22.md; do
       printf '\n<details><summary>%s</summary>\n\n' "$f"
       cat "$f"
       printf '\n</details>\n'
     done
   } > ledgers.md
   gh issue create --repo thekaveh/NNx --title "Maintenance ledgers of 2026-07-01 and 2026-07-22 (archived)" --label documentation --body-file ledgers.md
   gh issue close <the new issue number> --repo thekaveh/NNx --reason completed
   ```

2. `git rm -r .maintenance`, and link the new issue in the PR body.

**If option C, the worker does:**

1. In each of `.maintenance/overnight-2026-07-01.md` and `.maintenance/overnight-2026-07-22.md`, insert after the `# 1. …` title line and its blank line:

   ```markdown
   > **Historical record.** This ledger records one maintenance run as it stood
   > on its date. It is not kept up to date: branches, files, tools and CI
   > settings it names may have changed or gone since. Do not add new reports
   > here.
   ```

   followed by one blank line, before the existing `**Status:**` line.

**Worker setup.** No torch needed (docs/config only).
